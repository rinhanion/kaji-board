# kaji-board の RDRA

Issue: #33

要件定義の手法 RDRA(Relationship Driven Requirement Analysis)で、今の kaji-board を整理し直したもの。
できあがっているシステムを、RDRA の形で見えるようにする(「既存システムの可視化」)。コードは変えていない。

## RDRA のあらまし

- システムにかかわる要素(人・業務・画面・情報・状態など)を図に並べ、**要素どうしのつながり**をたどって、要件の抜けや食い違いを見つける
- 要素は 4 つの視点に分かれる。外側の視点が内側の「なぜ」になる。どの要素も、つながりをたどると外側の「なぜ」まで行き着くのがよい形
- まず粗くても全部を埋め、つながりを見ながら何周かして精度を上げる

## 4 つの視点と 9 つのモデル

| 視点 | 問い | モデル | ファイル |
| --- | --- | --- | --- |
| システム価値 | だれに、どんな価値を届けるか | システムコンテキスト、要求モデル | [1-システム価値.md](1-システム価値.md) |
| システム外部環境 | システムの外で、人はどう動いているか | ビジネスコンテキスト、ビジネスユースケース(BUC)、業務フロー | [2-外部環境.md](2-外部環境.md) |
| システム境界 | 人とシステムはどこで接するか | UC 複合図(ユースケース・画面・イベント) | [3-境界.md](3-境界.md) |
| システム | システムは何を覚え、どう変わるか | 情報モデル、状態モデル、バリエーション・条件 | [4-システム.md](4-システム.md) |

見直しで見つかった抜け・ずれ・疑問は [5-気づき.md](5-気づき.md)。

## 今回の起こし方

公式サイトの「既存システムの可視化」の進め方に沿った。

- **上から(入出力・データから)**: 画面とシートを並べ、そこから UC を出し、UC を使うアクターを出す。Cron のようなイベントから外部システムを出す。テーブルは、そのまま情報にせず、業務で扱う単位(家事・家族など)にまとめて情報にし、情報から状態を出す
- **下から(ソースから)**: `src/index.ts` の `/api/*` と `public/*.js` を、UC への索引にして、上から出したものとつなぐ
- **条件には、仕組みのためのルールを入れない**: 合言葉の HMAC、20 秒ごとの読み直しなどは条件にしない。「4:00 で日が変わる」「ありがとうは 1 人 1 回」のような、家族にとっての決まりだけを条件にする

## 図の読み方

- 図は Mermaid で書いてある。GitHub や Obsidian ではそのまま図になる
- 各ファイルの終わりの「つながり」の表で、ほかの視点の要素とのつながりを書いている

## 地図を今のシステムと合わせる

- 進め方(要件定義・地図を畳む)は、スキル `.claude/skills/rdra/SKILL.md` にある
- `npm run check` の中で `scripts/check-rdra.mjs` が走る。次のずれがあると落ちる
  - `src/index.ts` の API と、[3-境界.md](3-境界.md) の「UC の一覧」の API が合わない
  - `migrations/` のテーブルが、[4-システム.md](4-システム.md) の「情報モデル」に無い
- 条件・状態・BUC のずれは機械では見られないので、`reviewer` が見る
